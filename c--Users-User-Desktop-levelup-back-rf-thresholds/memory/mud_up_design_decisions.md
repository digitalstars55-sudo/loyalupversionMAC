Эти решения нетривиально вытекают из контекста и не разработчик «по умолчанию» сделает иначе. Не менять без обсуждения с юзером.

## 1. RF в виде Bento + тогл на матрицу
**Почему:** Юзер сравнивал варианты «классическая 4×3 матрица как в вебе» / «список карточек» / «гибрид» / «свайп по уровням» и выбрал **Bento + тогл** — рекомендованный мной как баланс между обзором и mobile-native UX.
**Как применять:** При добавлении новых аналитических экранов ориентироваться на тот же паттерн (hero + medium + compact). Чистая матрица доступна как «power-user view» через 📊-иконку.

## 2. Объединённый «совет + стратегия» в DetailCard
**Почему:** Юзер сказал «интуитивно непонятно» про прежнюю версию где hint и strategy были двумя отдельными карточками. Объединил в один жёлтый бокс с тонким разделителем и подзаголовками «СОВЕТ ПО РАССЫЛКЕ» / «СТРАТЕГИЯ».
**Как применять:** При добавлении новых полей в SegmentInfo (например, KPI-метрика) вписывать их в этот же advice-блок, а не плодить новые контейнеры.

## 3. Senler-ссылка убрана из главных кнопок DetailCard в BroadcastModal
**Почему:** На мобайле скачивание TXT-файла через ссылку UX-боль (Downloads-папка скрыта). Сделал Senler тихой текст-ссылкой внизу BroadcastModal.
**Как применять:** Любые «скачать файл» действия на мобайле — через Share Sheet или вообще не размещать на главных экранах.

## 4. Emoji вместо текстовых лейблов в ячейках матрицы
**Почему:** Текстовые подписи «ЧЕМПИОНЫ R3 F3» в ячейках 73px шириной нечитаемы на SE 320. Заменил на emoji + count + pct. Имена сегментов всё ещё доступны через 📖 LegendSheet и DetailCard.
**Как применять:** Список emoji зашит в `SEG` (`src/mocks.ts`), стабилен. Если бэк начнёт отдавать `segment_emoji` — использовать его, иначе fallback на SEG.

## 5. Запрет закрытия негативного отзыва без ответа
**Почему:** Юзер дважды сказал что это плохо («почему негативный отзыв отметить решённым если не ответа»). Сначала я добавил жёсткое предупреждение, потом убрал кнопку совсем для VK+негатив+неотвечено.
**Как применять:** В `ReviewDetailModal.tsx` логика в `closeMode`: если `forbidden` — кнопки нет, показывается `requireReplyHint`. Не возвращать кнопку без согласия юзера. Если админ решил вопрос оффлайн — пусть напишет «связались по телефону, проблема решена» — это лучше тишины.

## 6. Контакты менеджера — отдельная страница в Ещё, не редактируется юзером
**Почему:** Юзер спросил «где задавать номер менеджера». Объяснил: контакт назначает Levelup-команда через свою внутреннюю админку, в БД хранится `TenantManager`-запись. Мобайл только отображает — read-only.
**Как применять:** На странице `ManagerContact` намеренно нет полей редактирования. Если юзер попросит — это значит он не понял продуктовый флоу, нужно мягко объяснить.

## 7. AI-черновик автоответа — всегда требует апрува, не отправляется автоматически
**Почему:** На вопросе «что если не ответил на пуш» юзер выбрал вариант (a) — никогда без апрува, просто напоминать через интервал. Пункт «авто-отправка через X минут» отвергнут.
**Как применять:** В `AutoReplySettings` есть только настройка интервала напоминания, нет переключателя «авто-отправлять после N минут». Не добавлять — юзер явно выбрал безопасный режим.

## 8. AI-черновик идёт через бэк-AI, не шаблоны из БД
**Почему:** На выборе из A (шаблоны)/B (AI на лету)/C (гибрид) юзер выбрал B. Источник черновика — AI-генерация по контексту отзыва.
**Как применять:** Бэк должен дёргать AI-провайдер при создании черновика. Шаблоны в БД заводить не нужно.

## 9. Все тональности кроме SPAM попадают в auto-reply
**Почему:** Юзер выбрал «все тональности кроме спам».
**Как применять:** В `AutoReplySettings.sentiment_enabled` нет ключа SPAM (всегда выключен), интерфейс показывает «Игнорируется всегда» серым.

## 10. Mock-данные доставки отличаются от ресторана
**Почему:** Юзер заметил «доставка такой же анализ как у кафе?». Доставка обычно генерирует больше разовых заказчиков (F1) и меньше постоянных (F3). Сделал MOCK_DELIVERY с total 1854 vs 2847 для restaurant, F1 в 2 раза больше, F3 в 3-4 раза меньше.
**Как применять:** Это mock — реальные данные с бэка должны иметь похожие пропорции.
