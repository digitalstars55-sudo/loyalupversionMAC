# Доработка RF-матрицы — RF Thresholds & Mass-Apply

Этот патч решает три задачи из ТЗ:

1. **Настройки порогов для режима «Все точки».** В `RFSettings` появилась
   возможность создать запись с `branch=NULL` — это и есть «Все точки».
   Когда пользователь выбирает в RF-аналитике этот режим, матрица
   строится по её порогам, а не по дефолтным.

2. **Корректное отображение порогов в админ-панели клиента.**
   Заголовки строк/колонок матрицы (`F1: 1–3 виз.` и т. п.) теперь
   строятся из реальных порогов выбранной области, а не из захардкоженных
   констант. Подсчёт гостей в каждой ячейке тоже идёт по этим порогам:
   из стораженых `recency_days`/`frequency` пересчёт R/F выполняется
   «на лету» при каждом запросе.

3. **Массовое применение настроек.** В админке `RFSettings` появились:
   - чекбокс **«Применить настройки ко всем кафе»** на форме редактирования —
     ведёт на отдельную страницу подтверждения с превью значений и
     списком затронутых точек;
   - две `admin actions` на changelist:
     - «Применить пороги выбранной записи ко **всем** точкам»;
     - «Скопировать пороги из «Все точки» в **выбранные** записи».
   - При сохранении точечных настроек никакой fallback к «Все точки»
     не происходит — приоритет остаётся у точечных настроек.

## ✅ Деплой (важно!)

В этом проекте файлы миграций **не хранятся в git** — они перечислены
в `.gitignore`:

```
**/migrations/*
!**/migrations/__init__.py
```

Это значит: миграции генерируются на сервере при каждом деплое.
Поэтому **никакой ручной `0002_xxx.py` миграции в патче нет** — Django сам
сгенерирует нужную миграцию по новым моделям при выполнении
`makemigrations analytics`.

### Шаги деплоя

```bash
# 1. Получить новый код
git pull

# 2. Активировать окружение (или зайти в контейнер)

# 3. Сгенерировать миграцию для analytics — Django сам увидит
#    новые поля порогов, nullable branch и UniqueConstraint.
python manage.py makemigrations analytics

# 4. Применить миграции ко ВСЕМ тенантам.
python manage.py migrate_schemas
# (или если у вас есть отдельная команда — используйте её)

# 5. Перезапустить web/celery (по обычной процедуре).
```

**Важно для существующего prod:** если у вас уже есть применённая
миграция `0001_initial.py` с прежней версией `RFSettings` (без полей
порогов), `makemigrations analytics` сгенерирует НОВУЮ миграцию
(например, `0002_*`) с операциями `AddField`/`AlterField`/`AddConstraint`,
которые мягко надстраиваются над существующей таблицей. Django сам
правильно построит дельту — ничего ломать руками не нужно.

**После деплоя:**
1. Откройте **Аналитика → RF-настройки** в админке.
2. Создайте запись с пустым полем «Торговая точка» — это будут общие
   настройки «Все точки». Задайте пороги и сохраните.
3. Если хотите сразу раскопировать на все кафе — поставьте галочку
   «Применить настройки ко всем кафе», сохраните, и на промежуточной
   странице нажмите «✅ Подтвердить и применить ко всем».
4. После значимых изменений порогов запустите **🔄 Пересчитать**
   из RF-аналитики — обновятся `r_score`/`f_score`/`segment` у гостей
   и снапшоты. (Сама матрица всегда пересчитывает r/f «на лету»,
   поэтому смена порогов сразу видна визуально.)

## Логика разрешения порогов (приоритет)

`RFSettings.resolve_for_scope(branch_ids)` возвращает
`(settings_obj, thresholds_dict, source)` где `source ∈ {'branch', 'global', 'default'}`:

1. **branch** — если в `branch_ids` ровно одна точка и для неё есть
   `RFSettings(branch=X)` → используются её пороги.
2. **global** — иначе берётся запись `RFSettings(branch=NULL)`
   («Все точки»), если она существует.
3. **default** — иначе используется `RF_DEFAULT_THRESHOLDS`
   (R3≤14 / R2≤30 / R1≤60 дн., F1≤3 / F2≤5 виз.).

При мульти-точечной выборке (`branch_ids = [1, 2, 3]`) приоритет
сразу — `global` → `default` (per-branch здесь неоднозначно).

## Что НЕ менялось (умышленно)

- `RFSegment.recency_min/recency_max/frequency_min/frequency_max`
  оставлены как есть. Эти поля уже не влияют на реальную классификацию
  гостей (она идёт через `_RF_TO_CODE` + per-scope thresholds), но
  остаются для обратной совместимости и документации.
- `_R_META` / `_F_META` остались в коде как fallback'и для случая, когда
  пороги не переданы — сигнатура `_r_score(d)` / `_f_score(v)` без
  `thresholds=` продолжает работать как раньше.
- Сигнатура публичного `recalculate_rf_scores` сохранена —
  добавлены только новые ключи в возвращаемый dict.

## Известные особенности производительности

- `get_rf_segment_guests` пересчитывает r/f каждой записи в Python
  (через `qs.iterator()`), а не фильтрует в БД. Для тенантов с
  десятками тысяч гостей и редкими сегментами это может слегка
  замедлить открытие списка гостей по ячейке. Если это станет проблемой —
  можно после `recalculate` использовать сохранённые `r_score`/`f_score`
  как первичный фильтр и проверять «на лету» только candidate-ов.
  Сейчас это OK для большинства тенантов и обеспечивает 100% корректность
  при только что изменённых порогах.

- Аналогично для `get_rf_summary_stats` — итерация по всем строкам
  через `.values()`, что норм до ~100k гостей на тенант.
